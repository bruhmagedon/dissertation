**Я бы сохранил стенд и пересмотрел центральный вопрос магистерской.** Опыт `3 → 1` выполнил свою задачу. Ты разобрался, как изменение проходит по графу, и научился видеть разницу между обращением к значению и выполнением функции. Раньше я слишком быстро предложил сделать окупаемость сравнения массивов основной линией диссертации. После просмотра кода и ближайших аналогов я вижу более содержательный вопрос:

> **Можно ли по записи работы интерфейса определить, в каком месте графа стоит проверять неизменность результата, чтобы ускорить реальные действия пользователя? И насколько хорошо такая рекомендация работает на других действиях?**

Здесь появляется конкретный адресат — разработчик, которому нужно ускорить экран. У метода есть вход — граф вычислений и запись взаимодействий. Есть выход — рекомендация для конкретного участка кода, включая вариант «оставить как есть». А правильность рекомендации можно проверить экспериментом. **Это кандидат на исследование. Научную новизну самого метода пока рано считать установленной.**

## 1. Почему нынешний опыт ощущается как песочница

Я посмотрел приложенный `dissertation.zip`, прежде всего `experiment.ts`, `trace.ts`, экспорт сравнений и тесты. Это разбор исходников, приложение я в этот раз не запускал. В коде нашлась деталь, которая хорошо объясняет твоё сомнение.

Продажи в одном прогоне фиксированы. Пользователь меняет только нижний порог. При повышении порога какие-то продажи могут только выпасть, при понижении — только добавиться. **Из этого следует, что в твоём конкретном эксперименте две выборки с одинаковой длиной уже имеют одинаковый состав и порядок.** Предположим, порог повысили. Новая выборка целиком содержится в старой. Если длина прежняя, ни одна запись не выпала. Это справедливо и для повторяющихся сумм.

А твой режим `reuse-array` при равной длине дополнительно проходит по всем элементам через `every`. Для текущего графа существует более дешёвая проверка, которую можно вывести прямо из постановки. Кроме того, у тебя `count` читает `.length`, а `sum` проходит массив через `reduce`. Поэтому два сэкономленных вызова уже **в собственном коде стенда** имеют очень разный вес. Наконец, `execute()` после каждой операции создаёт снимок через `structuredClone` всего накопленного журнала. Если замерить этот метод целиком, в результат попадёт растущая стоимость истории.

Это объясняет, почему увеличение числа продаж с четырёх до ста тысяч само по себе мало что меняет в научной постановке. Ты всё ещё исследуешь один порог, один доступный выход и одну заранее выбранную точку оптимизации. **При этом стенд уже умеет ровно то, что пригодится дальше:** повторить одинаковую последовательность действий на свежих графах, различить чтение и пересчёт, показать, откуда взялся результат. Эту часть я бы оставил.

## 3. Какую реальную задачу я бы выбрал для тебя

Возьмём экран, который тебе знаком по фронтенду, — **таблица сотрудников с фильтрами, сортировкой, пагинацией и сводкой по отделам**. Для первого исследования достаточно локального набора данных, который браузер действительно фильтрует и группирует. Это существенно: если всю работу выполняет сервер, измерять клиентскую фильтрацию на таком экране бессмысленно.

Пусть у сотрудника изменился номер телефона. Возможны разные последствия:

- Строка с этим сотрудником должна показать новый телефон.
- Список ID сотрудников, прошедших фильтр по отделу, может остаться прежним.
- Сводка численности по отделам тоже может остаться прежней.
- Если пользователь изменил отдел сотрудника, и список, и сводка уже могут измениться.
- Если сводка закрыта и её значение никто не запрашивает, цена её потенциального пересчёта в этом действии может быть нулевой.

Теперь у разработчика есть **реальный выбор места проверки**. Сравнивать весь массив сотрудников? Стабилизировать только список ID? Сравнивать результат группировки по отделам? Оставить стандартное поведение? Два последних экрана могут выглядеть одинаково при любом из этих решений, а затраты будут разными.

Здесь есть и содержательное ограничение корректности. **Возвращать прежний массив объектов сотрудников только потому, что совпали ID, опасно:** тогда строка может показать старый телефон. Зато для узла, чей результат по определению состоит *только из ID*, сравнение последовательностей ID корректно. Так возникает конкретная архитектурная задача — выбрать **узел с подходящим смыслом результата**, для которого допустима проверка равенства и от которого зависят достаточно дорогие вычисления.

Для ветки преподавателя **«известная задача → новый метод»** я бы сформулировал так:

| Вопрос | Рабочий ответ |
|---|---|
| **Какая задача известна?** | Сократить время обновления производных данных интерфейса при сохранении правильных результатов всех запрошенных представлений. |
| **Какое решение должен принять метод?** | Для заданного экрана и набора действий выбрать один узел из нескольких допустимых кандидатов, где проверка равенства результата даст наибольший выигрыш. Допустимый ответ — ни один. |
| **Что получает метод?** | Запись действий, явно прочитанные выходы, зависимости между вычислениями, наблюдения о равенстве результатов и оценки стоимости операций. Корректный способ сравнения указывает разработчик. |
| **Что выдаёт?** | Например, «проверять список ID после фильтрации». К рекомендации прилагается объяснение, какую работу это позволяет пропустить и на каких действиях проверка добавляет затраты. |
| **Где кандидат на новизну?** | В способе оценки **предотвратимой работы дальше по графу** по записи взаимодействий с экраном, с учётом общих зависимостей, других причин пересчёта и реально запрошенных выходов. |
| **Как проверить качество?** | На небольшом графе включить проверку по очереди в каждом кандидате, измерить реальные времена и узнать лучший вариант. Затем проверить, насколько близко метод подошёл к этому выбору на другой записи действий. |

Рабочее название для разговора: **«Выбор узлов для проверки равенства результатов в реактивных графах веб-интерфейсов по трассам пользовательских действий»**. Его можно произнести проще: **«Я исследую, как по работе экрана определить, где выгодно останавливать лишние пересчёты»**.

## 4. В чём именно мог бы состоять твой метод

Представь, что профилировщик показал дорогую группировку по отделам. Это отвечает на вопрос, *где потрачено время*. Разработчику нужен другой ответ: *какое изменение в коде позволило бы избежать этой работы?* Дорогая группировка может каждый раз честно получать новые данные. А может десять раз подряд получать одинаковый по смыслу список из-за более раннего узла. Именно разрыв между «где дорого» и «что здесь можно предотвратить» авторы MemoizeIt выделяют применительно к поиску возможностей мемоизации. [software-lab.org](https://software-lab.org/publications/oopsla2015.pdf?utm_source=chatgpt.com)

**Отличие твоего кандидата от MemoizeIt** можно сформулировать точно. MemoizeIt ищет вызовы метода, результат которых можно переиспользовать для повторяющихся входов. В твоём случае **вход узла может измениться, сам узел всё равно выполнится, но равенство его выхода позволит пропустить работу в других узлах**. Выгода находится дальше по графу. Это отличие от конкретной работы. Оно ещё не доказывает оригинальность относительно всей литературы. [software-lab.org](https://software-lab.org/publications/oopsla2015.pdf?utm_source=chatgpt.com)

Первую версию метода я бы ограничил **выбором одного места проверки**. Для каждого кандидата и каждого записанного действия он пытается ответить на три вопроса:

1. **Совпал бы выход узла с предыдущим?** Если нет, проверку оплатили и продолжаем пересчёт.
2. **Какие востребованные вычисления действительно удалось бы пропустить?** Если сводку не читали, экономия на ней равна нулю. Если итог зависит ещё и от другого изменившегося входа, его пересчёт может понадобиться в любом случае. Если две ветки используют один общий узел, его время учитывается один раз.
3. **Сколько стоит сама проверка?** У списка из десяти ID и у списка из пятидесяти тысяч цена разная. При разной длине сравнение может закончиться сразу.

Для кандидата \(v\) получается оценка:

\[
\text{ожидаемая экономия}(v)
=
\sum_{\text{действия}}
\bigl(\text{стоимость предотвратимых вычислений}
-
\text{стоимость проверки в }v\bigr).
\]

**Сложность и возможный вклад находятся в первом слагаемом.** Само вычитание затрат из выгоды тривиально. Исследовательская часть начинается там, где нужно по исходной записи оценить, что произошло бы при другом выборе, и затем проверить этот прогноз настоящим запуском. Например, простое правило «бери узел с наибольшим числом потомков» ошибётся, если половину этих потомков пользователь вообще не читает. А правило «бери самый дорогой узел» ошибётся, если его результат почти всегда меняется.

У меня **нет основания обещать**, что такая постановка окажется новой. В найденных работах есть по отдельности динамические рекомендации по мемоизации, настройка остановки распространения и учёт востребованности. Ближайший предмет дальнейшего поиска уже достаточно узок: *выбор места установки проверок равенства выходов по трассе востребованных вычислений*. Если найдётся готовый метод с тем же входом, выходом и критерием, его надо взять за прямой аналог и выяснить, где он ошибается на твоём классе графов. Именно так и ищут новый метод — находят конкретное решение, которое существующий подход принимает плохо, и предлагают правило, исправляющее этот случай. [software-lab.org](https://software-lab.org/publications/oopsla2015.pdf?utm_source=chatgpt.com)

## 5. Как быстро выяснить, достойна ли идея магистерской

**Я бы изменил следующее поручение агенту.** Раньше мы собирались добавить дорогую группировку, чтобы потенциальная экономия стала заметнее. Но если специально сделать ветку дорогой, а потом показать, что её выгодно пропускать, преподаватель справедливо спросит: «Вы сами устроили условия, при которых получился ожидаемый ответ». Сейчас важнее найти **два правдоподобных сценария одного экрана, в которых лучшим окажется разное решение**.

1. **Взять один экран с естественной нагрузкой.** Лучше всего — доступный пример приложения, где фильтрация и агрегация уже нужны пользователю. Если берёшь учебную таблицу сотрудников, задай поведение как у обычного продукта. Должны меняться и строки, и фильтры, и востребованность сводки. Зафиксируй происхождение данных и сценариев, чтобы было ясно, какие из них смоделированы.
2. **Выбрать два или три корректных кандидата.** Например, упорядоченный список видимых ID, список ID текущей страницы и сводка по отделам. Для каждого заранее запиши, что означает равенство и кто читает его результат. Проверь каждый отображаемый выход независимым полным расчётом. Проверка одного среднего пропустила бы ошибку со старым телефоном.
3. **Сначала измерить лучший выбор перебором.** На одинаковой последовательности действий запустить стандартный вариант и каждый вариант с одной проверкой. Использовать вычислительное ядро без React, подробного журнала и клонирования снимков в измеряемом участке. Чередовать порядок вариантов, повторять серии и сохранять разброс. Если речь в докладе пойдёт об отзывчивости самого экрана, дополнительно измерить действие в браузере до обновления представления.
4. **Сравнить два профиля использования.** Например, в одном пользователь листает и редактирует таблицу при закрытой сводке, в другом — активно меняет фильтры и смотрит распределение по отделам. В обоих случаях действия должны иметь смысл сами по себе. Смотри, меняется ли лучший кандидат и велика ли цена неправильного выбора.
5. **Только после этого строить метод.** Его соперники — стандартное поведение, простое правило по частоте совпадений и выбор по числу зависимых узлов. Лучший измеренный перебором вариант служит ориентиром. На новых последовательностях сравнивай **цену ошибки**: сколько времени потерял рекомендованный вариант относительно лучшего. Отдельно учитывай стоимость получения профиля и число пробных запусков. Если полным перебором решение находится так же дёшево, это существенное ограничение метода.

**У этого пилота должен быть исход, при котором ты откажешься от идеи.** Если на реалистичных сценариях разница тонет в разбросе, всегда выигрывает одна очевидная стратегия или эффект есть только на искусственно утяжелённой функции, я бы снял выбор точек сравнения с роли центральной темы. Если же на одном экране лучший выбор меняется вместе с действиями пользователя и простая эвристика заметно ошибается, у тебя появляется первый материал, который я бы действительно показал руководителю. Даже до разработки собственного метода.

## 6. Есть и другая ветка, если производительность тебя не увлекает

Из случая React Redux вырастает **самостоятельная тема про корректность**. Известная проблема — после сочетания кеширования и отслеживания зависимостей компонент может продолжать показывать старые данные. Исследовательский вопрос — как подбирать короткие последовательности действий, которые выявляют такие ошибки во взаимодействии селектора, кеша и нескольких потребителей. Результат понятен разработчику: воспроизводимый сценарий, на котором экран расходится с независимым расчётом. [GitHub](https://github.com/reduxjs/react-redux/releases?utm_source=chatgpt.com)

У этой ветки тоже высокая планка новизны. Уже есть межбиблиотечный набор тестов реактивности, исследования автоматического тестирования реактивных программ и реализации, проверяющие случайные графы относительно эталона. Значит, кандидат на вклад здесь — **стратегия выбора последовательностей именно для сочетания общего кеша, смены зависимостей и нескольких потребителей**. Её можно оценивать по способности выявлять заранее выбранные классы ошибок при одинаковом числе проверок. Это отдельная магистерская по тестированию. Из текущих наработок для неё особенно пригодятся исполнитель операций, журнал и воспроизведение шагов. [GitHub](https://github.com/johnsoncodehk/reactive-framework-test-suite?utm_source=chatgpt.com)

**Мой выбор для тебя сейчас — первый путь, с одной проверкой жизнеспособности до дальнейшей разработки.** Он сохраняет то, что тебе понравилось: полотно, на котором можно увидеть работу графа. И он даёт стенду назначение за пределами обучения: проверить, способен ли он подсказать разработчику конкретное изменение в конкретном экране и предсказать последствия этого изменения.

Когда захочешь обсудить направление с руководителем, его можно представить так:

> Я исследую обновление связанных данных в аналитических интерфейсах. Разработчик может останавливать повторные вычисления в разных местах графа, но каждая проверка сама занимает время, а польза зависит от того, какие части экрана использует человек. Я хочу проверить, можно ли по записи нескольких взаимодействий выбирать подходящее место для такой проверки. Сейчас у меня есть стенд, на котором виден механизм. Ближайший результат, который я хочу получить, — показать на одном прикладном экране, существует ли значимая цена неправильного выбора. Если существует, я смогу сравнить свой способ выбора с простыми правилами и с лучшим вариантом, найденным перебором.

Это уже утверждение, за каждую часть которого можно отвечать. А **первое, что стоит искать в коде и данных, — ситуацию, где у разработчика действительно есть трудный выбор**. Она даст теме больше оснований, чем ещё одна серия замеров на знакомом пороге.
