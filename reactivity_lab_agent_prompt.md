# Задание агенту. Лаборатория реактивных вычислений

Ты работаешь в существующем репозитории диссертации. Реализуй ранний исследовательский MVP, которым можно пользоваться самому и который можно показать на демонстрации. Пройди этапы последовательно до работающего сквозного сценария. Начни с проверки актуальной ветки, инструкций репозитория и уже реализованных возможностей. Используй этот документ как постановку задачи. Если имена файлов или детали интерфейса изменились, ориентируйся на фактический код.

## 1. Что должен уметь пользователь

Я открываю страницу «Сотрудники», вижу обычную рабочую таблицу, меняю отдел сотрудника, редактирую телефон, переключаю сортировку, открываю сводку. Стенд записывает действия. Я открываю одно из них на графе и вижу, какие данные пользователь действительно запросил и какие функции выполнились. Затем запускаю ту же запись с разными вариантами проверки равенства результатов. Для каждого варианта получаю ответ на три вопроса.

1. Остались ли правильными все результаты, которые видел пользователь?
2. Какие вычисления действительно удалось пропустить и сколько стоила сама проверка?
3. Как изменилось время выполнения всей последовательности и сумели ли мы заранее выбрать удачный вариант?

Итоговое решение метода — выбрать один узел для проверки равенства либо оставить базовый режим. Основная гипотеза состоит в том, что выбор зависит от действий пользователя и востребованных выходов. Совпадение победителей, отсутствие различимой разницы и ошибка прогноза — допустимые исходы. Все цифры в интерфейсе должны происходить из прогонов.

## 2. С чего начать в репозитории

В переданном снимке рабочая SPA находится в experiments/02-sales-graph. Изучи experiment.ts, trace.ts, comparison-export.ts, script.ts, src/App.tsx, src/Graph.tsx, src/CompareRuns.tsx, src/Hypotheses.tsx, тесты ядра и Playwright. Используй существующие команды Vite+, TypeScript, React Flow, тему, типографику, карточки, переключение вида, drawer и паттерн «открыть операцию на полотне».

Есть несколько существенных деталей реализации.

- Текущая операция read читает только average. Для предметного экрана у команды чтения должен появиться явный набор выходов. Существующие сценарии A/B и путь их запуска должны продолжать работать.
- execute() возвращает snapshotFromJournal(), который клонирует и обходит накопленный журнал. Для тайминга нужен путь выполнения без событий диагностики, копирования истории и построения снимков на каждом действии.
- union ComputedNode и сводки привязаны к filtered, sum, count, average. При добавлении предметного графа вынеси действительно общие сведения об узлах и выходах. Два типизированных описания опытов достаточны. Не превращай приложение в редактор произвольных программ.
- Текущие большие массивы в журнале представлены длиной и несколькими элементами. Такое превью годится для экрана. Проверять равенство по нему нельзя.
- Узел count читает length, sum проходит по массиву. Один запуск каждой из функций имеет разную стоимость. В старом опыте с фиксированными продажами и единственным нижним порогом выборки вложены друг в друга. Равная длина здесь уже гарантирует одинаковый состав. Сохрани опыт как контрольный пример и не переноси это правило на сотрудников.
- До изменений запусти доступные штатные проверки. Зафиксируй контрольные значения для продаж. После первого чтения и перехода 11 → 12 на втором чтении ожидаются 3 и 1 выполнения для двух исходных режимов. Для 10 → 11 ожидаются 4 и 4. Измеряемые времена заранее неизвестны.

## 3. Продукт и навигация

Организуй приложение вокруг трёх доступных по URL представлений. Подбери способ маршрутизации с учётом текущего статического хостинга, прямого открытия ссылок, обновления страницы и кнопки браузера «Назад». Существующий вход должен вести к рабочему стенду.

| Представление | Основной объект | Главное действие |
|---|---|---|
| Лаборатория | Полотно графа и операция | Проследить, что пересчиталось и почему |
| Сотрудники | Рабочая таблица и сводка по отделам | Выполнить и записать действия на предметном экране |
| Исследование | Запись, кандидаты, серии и прогноз | Сравнить варианты и проверить рекомендацию на другой записи |

Оставь полотно главным содержимым лаборатории. Компактная навигация не должна конкурировать с нижней панелью операций. Для продаж сохрани знакомые управление порогом и выбор A/B. Для сотрудников покажи название записи и навигацию по действиям. Сравнение единичной операции можно оставить в существующем drawer. Таблицу результатов серии, параметры замера и проверку прогноза помести на отдельную страницу, где достаточно ширины.

Сделай замкнутый пользовательский путь. Из строки результатов можно открыть конкретное действие подходящего диагностического прогона на полотне, а затем вернуться к тому же сравнению, сохранив выбор. На узком экране второстепенные панели открываются по запросу. Кнопки с иконками имеют доступные названия, активный режим читается без различения цветов. Предусмотри пустую историю, незавершённую запись, выполнение серии, отмену, ошибку эталонной проверки и неразличимый результат. Покажи, какие данные синтетические и какая именно среда выполняла замер.

## 4. Предметный экран и вычислительный граф

Реализуй локальную таблицу сотрудников. Это работающий предметный пример на синтетических данных. Поля — стабильный ID, имя, отдел, должность и телефон. Действия — поиск по имени, фильтр отдела, сортировка, смена страницы, смена телефона или отдела, открытие и закрытие сводки. Генератор по seed воспроизводит исходные записи, порядок, дубликаты имён и распределение по отделам. В сортировке используй детерминированное разрешение равенства по ID. После уменьшения числа страниц определи и проверь поведение текущей страницы.

Построй граф так, чтобы каждый узел имел понятный контракт. Например:

| Узел | Результат | Важные зависимости |
|---|---|---|
| Отбор | Упорядоченные ID подходящих сотрудников | Данные сотрудников, строка поиска, фильтр |
| Сортировка | ID в порядке отображения | Отбор, режим сортировки, актуальные значения ключей сортировки |
| Страница | Последовательность ID видимой страницы | Отсортированные ID, номер и размер страницы |
| Строки таблицы | Поля актуальных сотрудников для видимых ID | ID страницы и актуальные записи по ID |
| Сводка | Упорядоченные пары «отдел — число сотрудников» | Отбор и актуальная принадлежность сотрудников к отделам |

Уточни зависимости согласно фактической реализации. Изменение отдела при фильтре «Все» может сохранить список ID и изменить сводку. Изменение телефона может сохранить список ID и изменить строку таблицы. В обеих ситуациях новая информация должна дойти до потребителя. Если нормализация данных сама естественным образом устраняет часть пересчётов, используй и опиши это. Запрещено ухудшать базовую реализацию ради красивого выигрыша.

Предложи три одиночных кандидата: проверки в узлах отбора, страницы и сводки. Базовый вариант использует обычное поведение реализации. Для ID сравнивай длину и все ID в порядке. Для сводки — все пары по явно заданному порядку и содержимому. При совпадении возвращай предыдущий объект результата. В каждой конфигурации работает не более одной дополнительной проверки. Если сводка является конечным выходом без дорогих потребителей, экономия от стабилизации ссылки может быть близка к нулю. Сохрани это как проверку способности метода отклонить бесполезного кандидата.

## 5. Запись действий и независимый эталон

Введи воспроизводимую последовательность внешних команд. После завершённого пользовательского действия зафиксируй требуемые выходы. Открытая таблица запрашивает строки и данные для пагинации. Открытая сводка дополнительно запрашивает агрегаты. Закрытие сводки прекращает запросы к ней. Наблюдатель стенда, перерисовка React и просмотр старых событий не должны создавать дополнительные чтения. Явно укажи, как записывается поиск — например, после подтверждения строки пользователем. При воспроизведении соблюдай те же границы.

Добавь три коротких пресета с понятными действиями: редактирование карточек при закрытой сводке, анализ отделов с открытой сводкой, смешанная работа с поиском и пагинацией. Дай пользователю записать собственную сессию, закончить её, сохранить локально и повторить с начала. Экспорт и импорт JSON должны переносить описание данных, seed, версию схемы, действия и запрошенные выходы. При импорте проверяй структуру и совместимость, выводи конкретную причину ошибки. Начинай воспроизведение с того же состояния, включая страницу и видимость сводки.

Для проверки корректности напиши прямой расчёт на TypeScript: от исходных записей и текущего состояния полностью построить нужные результаты. Он должен быть независим от реактивных узлов, кешей и функций, в которых реализована проверяемая оптимизация. В отдельном контрольном прогоне сравнивай полные результаты после каждого запрошенного чтения. При расхождении укажи действие, выход и первое различие. Исключай такой вариант из сравнения скорости. Два ошибочных движка могут согласиться друг с другом, поэтому совпадения между ними недостаточно.

Добавь небольшой именованный набор «Разбор по шагам». В нём Анна (ID 7) и Борис (ID 9) работают в продажах, Вера (ID 15) — в поддержке. При сортировке по имени и размере страницы 2 видны Анна и Борис. Запись для демонстрации открывает сводку, меняет телефон Анны, переводит Бориса в поддержку и затем включает фильтр «Поддержка». После смены телефона пользователь видит новый номер и прежние количества 2 и 1. После перевода он видит тот же порядок ID и количества 1 и 2. После фильтра видны Борис и Вера — на экране снова две строки, но это другие ID. Покажи переход прямо в журнале. Конкретное число запусков движков установи по факту исполнения.

Отдельно от этого примера дай запустить один профиль на 100, 1 000 и 10 000 сотрудников с фиксируемым seed. Это стартовая сетка пилота. Генерируй действия с явными правилами выбора записей и проверяй, что запись выполнима при каждом размере. Для проверки переноса внутри профиля используй другие записи с тем же распределением действий; проверку при смене самого профиля выдели отдельно. В результатах покажи фактическую долю запросов сводки, изменений состава и порядка ID. Тогда можно объяснить, какие нагрузки действительно различались.

## 6. Два способа выполнять один опыт

Сначала доведи до рабочего состояния предметный пример на @preact/signals-core. Затем подключи Reselect как несигнальную реализацию на мемоизированных селекторах. Для Reselect достаточно иммутабельного состояния и createSelector. Исследуется вычисление производных данных. Redux-store и подписки React-Redux для этой задачи не требуются.

Оба движка должны получать одни и те же предметные операции, логические входы, функции преобразования и запрашиваемые выходы. Зафиксируй гранулярность входов: если Preact получает отдельные сигналы полей, у Reselect должны быть эквивалентные зависимости; если один использует общий снимок коллекции, нельзя сравнивать это с точечным доступом к каждой записи и приписывать разницу только библиотеке. Неизбежные различия опиши в паспорте конфигурации. Графовые вычисления выполняет библиотека.

В Reselect укажи отдельно политику кеша аргументов и результатов. Для сравнения с «последним результатом» настрой соответствующий кеш с одной записью. При использовании lruMemoize задавай resultEqualityCheck в memoizeOptions вычислительной функции. Обоснуй фактическую конфигурацию и зафиксируй версию в lockfile. Проверяй число выполнений именно функции, вычисляющей результат; вызов входного селектора, попадание в кеш и исполнение result function — разные события. У двух движков могут различаться трассы при одинаковых правильных значениях.

Основное сравнение — базовый режим против кандидатов внутри одного движка. Второй движок нужен для проверки переносимости наблюдения. Если обе реализации дают одинаковую рекомендацию, покажи это. Если различаются, открой обе трассы на одинаковом действии. Документация для реализации: https://reselect.js.org/api/lruMemoize/ и https://reselect.js.org/api/createSelector/.

## 7. Журнал и полотно

Сохрани два смысла существующего графа. Вид «Зависимости» показывает, откуда берутся данные. Вид «Порядок чтения» показывает наблюдаемые события одного действия. Отдельно фиксируй запрос выхода, явное чтение, выполнение вычислительной функции, применение компаратора и его результат. Для сравнения фиксируй причину раннего выхода и число просмотренных элементов в диагностическом режиме. Не приписывай библиотеке внутренний вызов, если обёртка видела лишь вычисление в рамках внешнего запроса.

При сравнении одного действия в двух вариантах покажи полученные значения, список фактически пропущенных или добавившихся выполнений и место, где вернули прежний результат. Подписи отличают «вызовы за действие» от «вызовов за прогон». В пошаговом просмотре закрытая ветка обозначается как незапрошенная. Не читай её ради подписи. Подсветка разницы включается по выбранной операции; первый рендер и навигация не меняют журнал.

## 8. Протокол измерений

Сделай один исполнитель предметных действий с диагностическим и измерительным путями. В измеряемой части исключи журнал, клонирование снимков, сравнение с эталоном, работу React Flow и экспорт. Фильтрацию, работу библиотеки, выбранную проверку равенства и необходимые чтения включи. Инициализацию и первое чтение измеряй отдельно или явно выноси за интервал. В обоих вариантах затраты на запись состояния учитываются одинаково.

Измеряй целый блок действий. Для очень коротких записей используй серию эквивалентных воспроизведений с восстановлением исходного состояния вне учитываемого интервала. Повтор одной команды поверх уже разогретого финального состояния меняет смысл опыта. Зафиксируй единицу — например, миллисекунды на одну полную запись из K действий. Из времени блока нельзя вывести p95 отдельного клика.

Предусмотри короткий пилот и расширенную серию. Сделай отдельный прогрев. В повторении запускай каждую конфигурацию на свежем графе, используй одинаковые seed и запись, чередуй или воспроизводимо перемешивай порядок вариантов. Сохраняй номер парного повтора и порядок. Серию можно выполнять отдельным CLI на том же ядре либо из интерфейса в изолированном исполнителе. Дай интерфейсу открыть результат CLI. Не объединяй измерения Node и браузера в одну выборку. В UI должны работать прогресс и отмена; незаконченная серия получает статус частичной.

Храни сырые времена, единицы, версии, движок, стратегию, сборку, доступные сведения о среде, размер данных, число действий и параметры прогрева. Показывай медиану, квартильный диапазон и парную разницу «базовый минус кандидат»; положительное значение означает экономию. Заранее задай настраиваемый порог практически значимой разницы и покажи его. Например, для исследовательской серии оцени 95%-й интервал медианы парных разниц бутстрэпом по независимым парам; фиксируй seed и способ расчёта. Для слишком короткого пилота показывай исходные числа и пометку о недостатке повторов. Когда знак разницы ненадёжен или эффект практически мал, интерфейс это сообщает. Не объявляй лучший режим при разнице на уровне шума.

## 9. Экспериментальный метод выбора узла

Реализуй исследовательскую гипотезу в виде проверяемого алгоритма. Вход — диагностическая запись базового режима, граф, запрошенные выходы, заранее разрешённые компараторы и калибровочные оценки стоимости. Выход — один кандидат или базовая стратегия, объяснение и оценка экономии. Никогда не выбирай кандидата по времени проверочной записи до фиксации прогноза.

Для каждого кандидата v и действия a оцени:
- совпал бы результат с предыдущим при фактическом вычислении v;
- какие реально выполненные в базовом прогоне функции дальше по графу можно было бы пропустить;
- сколько стоили бы эти функции и сколько добавляет сама проверка.

Начальная модель: S(v) = сумма по действиям [оценка времени пропускаемых функций − оценка дополнительных затрат проверки]. Для базового варианта S = 0. Правило выбирает кандидата с наибольшим достаточно положительным S. В остальных случаях оставляет базовый режим. Предусмотри объяснение для одного действия обычным языком.

Считай только достигнутые и востребованные ветки. Общий узел в одном выполнении учитывается один раз. Учитывай другую изменившуюся зависимость: сохранение ID страницы не отменяет обновления строки, если изменился её телефон. Если библиотека и так пропустила функцию в базовом прогоне, экономия там равна нулю. Не начисляй проверку на действие, где сам кандидат не вычислялся. Для MVP используй статический ациклический граф, чистые функции и явно заданные зависимости. Если часть решения нельзя надёжно восстановить из базового журнала, помечай оценку как приближённую и выводи расхождение на проверке. Все данные для модели должны иметь понятный источник. Стоимость узла калибруй отдельно на подходящих входах, исключая вложенное время вызовов других узлов, иначе оно будет посчитано дважды. Укажи, какие затраты реактивного ядра модель пока не учитывает.

Предусмотри две разные кнопки или последовательных действия: «Получить прогноз» по калибровочной записи и «Проверить прогноз» на другой записи. Храни прогноз вместе с конфигурацией до проверки. Диагностическая запись новой нагрузки допустима как вход только в отдельно подписанном эксперименте, где заранее оговорено, что такая информация доступна. Для основной проверки переноса последовательность, результаты и времена отложенной записи доступны только при валидации.

Сравни четыре правила: стандартное поведение; кандидат с наибольшей долей совпадений; кандидат с наибольшим числом зависимых узлов; предложенная оценка. Одинаково задай область кандидатов и разрешение ничьих. На небольшом графе измерь все одиночные варианты на отложенной записи. Получи ориентир — лучший измеренный вариант с учётом неопределённости. Выведи цену выбора: сколько миллисекунд на запись потеряно относительно него и какова разница с базовым режимом. При практически равных временах допустима группа сопоставимых вариантов. Покажи затраты на профилирование и калибровку отдельно. При трёх кандидатах полный перебор может оказаться удобнее самой модели — пользователю нужно видеть и это.

## 10. Результат в интерфейсе

На странице «Исследование» исходная конфигурация должна читаться одной строкой: предметный пример, движок, набор данных, профиль, запрошенные выходы. Ниже размести таблицу, где строка — политика, а колонки — корректность, число выполнений, медиана времени блока, разброс и разница с базовым режимом. Диагностические числа и времена привязывай к одной конфигурации, отмечай разные прогоны-источники. Не выводи несопоставимые результаты в один рейтинг.

Покажи один график, который отвечает на реальный вопрос: как меняется разница времени с базовым вариантом при разных профилях или размерах данных. Нужны единицы, нулевая линия и разброс. Если серии ещё не выполнялись, дай запустить короткий опыт. В карточке прогноза отдельно покажи предложенный узел, основание выбора, последующую проверку и цену ошибки. Разреши открыть исходные действия и обнаружить, например, что модель ожидала экономию на сводке, которая при другом поведении пользователя была закрыта.

## 11. Порядок реализации и приёмка

Делай вертикальные срезы и после каждого проверяй обычный пользовательский путь. Порядок важен: если следующие срезы требуют исправления ядра, сначала исправь и повтори контрольные опыты.

| Срез | Что должно работать к его завершению |
|---|---|
| 1. Основание | Продажи проходят прежние проверки. Прямой расчёт, исполнение действия, построение снимка и диагностическая запись имеют ясные границы. |
| 2. Предметный пример | На странице сотрудников можно изменить телефон и отдел, записать действия, открыть их на графе и воспроизвести на свежих данных. Эталон проверяет строки, порядок ID, пагинацию и открытую сводку. |
| 3. Выбор точки проверки | Все три кандидата и базовый режим доступны на Preact. Одинаковые входы и выходы подтверждены. Одно сравнение можно разобрать на полотне. |
| 4. Измерительная серия | На одном профиле выполняются парные прогоны, доступны сырые данные и импорт, график строится по факту. UI допускает отмену, частичный результат явно обозначен. |
| 5. Метод | Прогноз зафиксирован до проверки. На другой записи доступны результат перебора, простые правила, цена выбора и объяснение хотя бы одного успеха или расхождения, если оно наблюдалось. |
| 6. Вторая реализация | Те же команды, кандидаты и выходы работают на Reselect. Можно повторить серию и понять, сохранился ли вывод внутри этой реализации. |
| 7. Демонстрация | Одна короткая инструкция ведёт от редактирования сотрудника до сверки прогноза. Из чистой копии проекта воспроизводятся контрольный сценарий и короткая серия. |

Целевые проверки: замена телефона при прежних ID; смена отдела при открытой сводке и прежнем списке ID; другая выборка той же длины; изменение порядка тех же ID; пустая страница; закрытая сводка; повторное чтение; независимость кешей при повторе; корректность экспорта, импорта и отмены; одинаковые пользовательские выходы обоих движков. Добавь регрессионный пример с двумя путями к одному потомку, чтобы проверить отсутствие двойного зачёта экономии. Проверь, что просмотр истории, смена темы и перемещение графа не добавляют вычислений. Запусти сборку, проверки ядра, подходящие браузерные тесты и руками либо через браузер пройди основной путь на широком и узком экране.

В README опиши запуск, один экскурсионный сценарий по кнопкам, правила равенства, границы таймера, параметры кеша, формат данных и смысл прогноза. В итоговом ответе дай команды запуска, перечень завершённых срезов, реальные наблюдения по двум профилям и один вывод, который пока сделать нельзя. Если в доступной среде получилось выполнить только пилот, так и обозначь. Исследовательский результат — воспроизводимое сравнение с возможностью проверить и опровергнуть прогноз. Научная новизна обосновывается отдельно по литературе и результатам работы.
